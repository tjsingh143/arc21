# Arc 21 — Audit

Date: 2026-08-15 · cosmetics, app art and onboarding rows updated 2026-08-18 (phase 14, session 1)
· rate limiting, the authorization surface, migration recovery and the daily tie-breaks updated 2026-08-18 (phase 14, session 2)
· network faults, reconnect, stale-version recovery and the password-reset deep link updated 2026-08-21 (phase 14, session 3)

An end-to-end check of whether this project is actually where the status
documents claim it is. Written because a fair question was asked: the server
layer typechecked and had passing tests for a whole turn while **every single
command returned 500**. That is a real failure of reporting, and this document
exists to make the difference between "compiles" and "works" explicit.

## The rule this audit applies

> A green test suite proves the code you wrote does what you told it to do.
> It proves nothing about whether the feature works, whether the screen renders,
> or whether anything is connected.

Every claim below is therefore graded by **how** it was verified, not by whether
a test passed.

---

## Verification levels

| Level | Meaning |
|-------|---------|
| **RAN** | Exercised against the real thing — the running app, the running database, the running function |
| **TESTED** | Covered by automated tests that assert real behaviour |
| **COMPILES** | Typechecks and is imported, but never executed |
| **ABSENT** | Not built |

## What this audit found and fixed

### The authorization gate had stopped running sixteen migrations ago

`20260813121200_hardening.sql` is the strongest idea in this schema: DO blocks
that **fail the migration** if a client role gains a privilege it should not
have. A check that runs on deploy beats a test somebody might not run.

It runs thirteenth of thirty-two. Everything applied after it — friends, rooms,
matchmaking, the daily challenge, leaderboards, cosmetics, notifications — has
never been checked by anything. The gate did not weaken. It simply stopped being
asked, and nothing said so.

Measured against the running database:

```
gate asserts: anon may execute exactly ONE public function
reality:      anon could execute SEVENTEEN
```

including `leaderboard_weekly_xp`, `leaderboard_daily_challenge`,
`my_leaderboard_position`, `my_strategy_accuracy_progress` and
`caller_is_room_member`.

The cause is one missing line, and it is a line that is easy to leave out because
the migration reads correctly without it. A newly created function carries
Postgres's **default ACL, which is `EXECUTE TO PUBLIC`**. The early migrations
all wrote

```sql
revoke execute on function … from public, anon;
grant  execute on function … to authenticated;
```

and the later ones wrote only the `grant` — which adds a privilege without
removing the default one.

Nothing was exploitable through it: the leaderboard store refuses to read a board
without a session, and every "my …" function derives the caller from `auth.uid()`
and raises when it is null. But the grant said one thing and the product did
another, which is the same shape as every other defect in this document.

The fix is not a longer allowlist. It is one mechanical rule —
**no function in `public` may be executable by `PUBLIC`** — which catches every
instance of this mistake including the ones nobody has made yet. The gate is now
a callable function, run at migration time and from pgTAP, and each of its eight
checks was proved to fail on a real breach before it was trusted.

### `RATE_LIMITED` had a message, an HTTP status, and no producer

The tenth instance of the pattern this document exists to track.
`CommandRejectionCode` has carried `RATE_LIMITED` since the contract was written.
`command-errors.ts` maps it to "Too many requests. Try again in a moment." and to
HTTP 429. `grep` across the whole repository found **no throw site anywhere** —
the only other matches were the auth store handling Supabase's own 429, which is
a different thing entirely.

`docs/SECURITY.md` meanwhile described the application's rate limiting in the
present tense: "Application-level limits cover friend requests per hour, room
creation per minute and hour, room join attempts per minute…". None of it
existed. Stale copy in a security document is the same defect as the onboarding
screen that told players accounts did not exist, and it is worse in kind: it is
the one a reader is most entitled to rely on.

### A rate limit consumed in the caller's transaction charges nobody for a failed guess

Found while building it, and it changed the design.

Five of the six limited actions charge an attempt that then SUCCEEDS, so
consuming inside the caller's transaction is fine. A room join is the opposite:
the attempt worth limiting is the one that FINDS NOTHING, because that limit is
what makes guessing a six-character code impractical. And an unknown code raised
— which rolls the whole call back, including the row recording the attempt.

Written that way, `join_private_room` would have had a rate limit that charged
only successful joins: a guesser's budget would have been infinite, and the
limit would have existed and enforced nothing. A pgTAP test of the boundary would
have passed.

`join_private_room` now returns no row rather than raising, so the attempt
commits and counts. That also closed a small oracle already present: "that table
is full" told a guesser their code had hit a real live room, while "that table is
not available" told them it had not. There is now one answer for every reason a
code does not admit you.

### `create or replace function` silently reverts every later redefinition

Self-inflicted, caught by the integration suite, and worth writing down because
it will happen again.

Adding a limit to five existing functions meant replacing their bodies. Two of
them had already been redefined by a LATER migration than the one they were first
written in — and the first draft copied the earlier version of each:

- `send_friend_request` lost the `notify_user` call that
  `20260817400000_notification_delivery.sql` added, so a friend request stopped
  producing a notification. Six integration tests failed and said so.
- `create_private_room` lost the `expire_stale_rooms()` call that
  `20260816130000_expire_rooms_on_use.sql` exists entirely to add. **Nothing
  failed.** No test covers that path, and it would have shipped: abandoned
  lobbies would have started holding their six-character codes for ever again,
  silently undoing a whole migration.

The lesson is mechanical. Before redefining a function,
`grep -l 'create or replace function public.<name>' supabase/migrations/*.sql`
and start from the LAST file, not the one where it was introduced.
`19_rate_limits.test.sql` now asserts both calls are still present in their
function bodies — not behaviour, just that the call is still there, which is
exactly what a wholesale replacement removes.

### The daily challenge graded every decision and recorded none of them against the attempt

The grading was not the missing part, which is why this stayed ABSENT for a
phase. `decision-grading.ts` has graded every decision at a ranked table since
phase 12, `daily_challenge` is in `ACCURACY_ELIGIBLE_MODES`, and every one of
those decisions went into `player_decision_periods` for the weekly strategy
board.

But the week bucket mixes in every solo and public-table decision the player made
that week, so it cannot answer the question the daily board asks. The ENTRY had
to carry its own figures and carried none. `evMistakeForDecision` — which prices
exactly what a wrong play cost — had been sitting in the strategy module with one
caller, a learning drill, since the tables were generated.


### The sound adapter had no call sites at all

`src/lib/audio/audio.ts` had shipped since phase 4 with a doc comment saying the
adapter was wired and "the call sites are correct — the sounds arrive by dropping
in files". A single grep settled it: `playSound` was exported and **never
invoked, anywhere**. Dropping in files would have produced silence.

The same phase's Settings screen said sound cues were "wired to every table
event". Neither statement was checked by anything, because a sound that is never
requested cannot fail a test.

There are nine call sites now, and each is asserted to exist by the union in
`audio.ts` matching the generated files exactly — a cue with no file, or a file
with no name, fails `tests/audio`.

### Three screens described a build that had stopped existing

The audit for "loading, empty and error states" turned up something worse than a
missing spinner: copy that was true when written and had quietly become false.

- **Onboarding** answered both account buttons with "there is no Arc 21 account
  service in this build". `app/(auth)/create-account.tsx` had existed since phase
  8. The single most-visited screen in the app was telling every new player that
  a working feature did not exist.
- **Profile** passed `hasAccount: false` as a literal, with a comment saying
  "when sign-in exists, this is the one line that changes". It did not change.
  Every signed-in player saw the guest profile, and `my_level_progress` — built
  one phase earlier — had no caller at all.
- **Settings → Privacy** said "there is no account in this build, so none of it
  is uploaded". A false privacy claim is the worst kind of stale copy: it is the
  one a reader is most entitled to rely on.

Each had a passing test beside it. The onboarding test asserted that the copy
still matched `/no Arc 21 account/i` — so it verified the sentence, not the
world. It now asserts reachability instead: both options lead to a route, and
neither claims an absence.

### A Maestro loop that could deadlock, and had been able to for months

`career-node.yaml` failed intermittently and had been treated as flaky. It was
not. The tap that starts the next hand was nested inside the betting branch, so
an iteration arriving at a settled hand skipped the entire body — and every
iteration after it did the same, because nothing else brings the betting bar
back. The flow then spent its remaining budget dumping the view hierarchy at a
table that could not move.

Diagnosed from the failure's own artefacts rather than by re-running: the last
hierarchy showed `Hand 2 of 10` with `Next hand` plainly on screen. Each state is
now handled at the top level of an iteration, and the iteration count came down
from 40 to 20 because a robust pass carries a whole hand.

### A test that asserted a place on a global leaderboard

"This player appears in the top 100 by weekly XP" passed for as long as the local
database had fewer than a hundred players with more XP than three hands earn.
Once integration runs had accumulated past that, a correct leaderboard failed a
correct test. This is the same mistake the pgTAP suite made a phase earlier, one
layer up. It now asserts the relationship — `my_leaderboard_position` agrees with
the board when the player is on the visible page, and reports a real rank when
they are not.


### The advisor could not run on the server, and the reason was not what was written down

The strategy leaderboard needs decisions graded by the server. The advisor could
not be imported into an Edge Function, and this repository had recorded the cause
as "a NEW file under `shared/` will not resolve" — close, but wrong, and wrong in
a way that made the problem look unfixable.

Working through it produced the actual rules, each one measured:

```
supabase/functions/_shared/probe/index.ts  ->  "./leaf.js"   FAILED
supabase/functions/_shared/probe/index.ts  ->  "./leaf.ts"   MOUNTED
_shared/*.ts -> ../../../shared/blackjack/hand-value.js      MOUNTED
_shared/strategy/*.ts -> ../../../../shared/blackjack/…      FAILED
```

So: inside `supabase/functions` a specifier must be a literal `.ts` path — a
`.js` one fails even for a file that is certainly present — while `shared/` files
resolve only at the exact depth the CLI already walks. The failure also happens at
`supabase start`, not at request time, which leaves the whole stack down and made
the earlier diagnosis harder than it needed to be.

The fix moves `shared/strategy` to `supabase/functions/_shared/strategy` and
leaves a one-line re-export barrel behind. The advisor was MOVED, not copied, so
invariant 7 still holds: one implementation of every rule.

### Decisions were never graded, and the column had been waiting since the first migration

`player_stats.decisions_total` and `decisions_optimal` have existed since
`20260813120100_profiles.sql`. Nothing had ever written them. Now every action at
a ranked table is graded from the state as it stood BEFORE the action:

```
solo: STAND actions sent    7
decision period row         {"decisions_total":7,"decisions_optimal":6}
lifetime player_stats       {"decisions_total":7,"decisions_optimal":6}
accuracy progress           {"accuracy_bp":8571,"minimum_required":100,"qualified":false}

private: STAND actions      2
host decision periods       []                    <- unranked, so nothing counted
```

Grading happens before `applyCommand`, because comparing the chart to a hand that
already has the hit card in it would grade the wrong decision. A `null`
recommendation counts as nothing rather than as a mistake, and a server-applied
timeout default is never recorded as the player's own choice.

### `profiles.level` was stored and never written

Found while wiring level-gated cosmetics. `shared/progression/xp.ts` says plainly
at the top of the file that total XP is the stored truth and the level is derived
from it — but the column existed anyway, and nothing wrote it. Every account sat
at level 1 forever, which meant:

* the high-stakes table gate (`level >= 10`) could never open;
* every level-gated cosmetic in the catalogue was unreachable.

It is now derived by a trigger, so the two cannot disagree:

```
0 XP -> 1     325 XP -> 3     999,999 XP -> 50
level 2 begins at 100, level 3 at 225, level 50 at 34,300
one XP short of any threshold names the level below
```

The SQL curve mirrors the TypeScript one, and
`tests/progression/level-curve.test.ts` recomputes the mirror independently and
asserts them equal at every level. A pre-existing pgTAP assertion that set
`level = 5` alongside 1,200 XP and checked the 5 was stored now checks that the
level is DERIVED — 1,200 XP is level 7, so the old row was internally inconsistent.

### A leaderboard is the easiest place to leak an account identifier

So the projection is asserted at the composite type rather than per query:

```
leaderboard_row: rank, display_name, avatar_asset_key, value, detail, is_you
```

No user id, no email, and no query can widen it. Measured against a live board:
no `@arc21.test` address appears in any response.

Two implementations of "my position" were rejected before the third. A lateral
join over a UNION was clever enough that reading it did not tell you whether it
was right; a temporary-table version was clear but made the function volatile and
failed at runtime with `CREATE TABLE is not allowed in a non-volatile function`.
The version that shipped is four plain queries, and a test asserts it agrees with
the board it is derived from.


### A private table minted chips
The chip-integrity lens was pointed at the closed economies before building two
more of them, and the first thing it found was a repeatable mint:

```
wallets before        25000 · 25000
started               private_table_started  stack 5000
wallets after seating 25000 · 25000   (correct — those chips came from nowhere)
LEAVE                 200 accepted
wallets after LEAVE   30000 · 25000
host ledger           initial_grant +25000, table_cash_out +5000
```

`settleTableClosure` credited `seatChipsAtTable(seat)` to the wallet with no
regard for where those chips came from. A private table seats every player on
5,000 chips that were never debited from anything — `buy_in` is 0 and
`escrow_chips` is 0, deliberately — so leaving one created 5,000 chips, once per
table, without limit.

The fix is not a check at the call site. `settleTableClosure` now reads the
session's mode from the row it is closing and refuses to move a chip unless that
mode is wallet-backed, because two call sites already reach it and the cost of one
of them passing the wrong answer is minting money.
`supabase/functions/_shared/session-economics.ts` is the only place that answers
the question, and it lists every mode exhaustively so a seventh has to be
classified to be playable. Re-measured:

```
wallets after LEAVE   25000 · 25000
host ledger           initial_grant +25000
RESULT: no chips minted.
```

A tournament seat holds 10,000. Had this been found after Phase 11 rather than
before it, the mint would have doubled.

### One player leaving ended the table for everyone
The same function set `phase = "SESSION_COMPLETE"` unconditionally. On a solo
table that is right; on a table with other people at it, it is a player being
thrown out of a hand they had money in:

```
guest bet 100         200 accepted
host LEAVE            200 accepted
phase after LEAVE     SESSION_COMPLETE
guest LOCK_BET        409 rejected SESSION_CLOSED
```

The closure now reports whether the TABLE ended, which is true only when no other
connected seat remains. After the fix the phase stays `BETTING_OPEN` and the
guest's `LOCK_BET` returns `accepted`. A tournament requires exactly this — three
people must keep playing when a fourth quits.

### No online table could reach hand two
The engine parks at HAND_COMPLETE on purpose, so a settlement is never animated
over, and expects its caller to start the next round. No client command mapped to
that, and `game-command` never called `beginNextHand`. Every server-authoritative
mode — solo, private, public — dealt exactly one hand and then stopped:

```
hand 1 finished             phase HAND_COMPLETE | hand 1
PLACE_BET at HAND_COMPLETE  422 WRONG_PHASE
RESOLVE_TIMEOUT             422 DEADLINE_NOT_REACHED
RESULT: the table cannot reach hand 2. No command advances it.
```

1,108 tests passed while this was true, because every one of them either drove the
engine directly or stopped after a single hand. A twelve-hand tournament and a
twenty-hand challenge were not "unbuilt" — they were unbuildable.

Fixed with a `NEXT_HAND` command, legal only at HAND_COMPLETE where no decision is
pending, plus a settlement rest window so a timeout can advance a shared table
whose players have gone quiet. Both routes call one function, so there is no
second place for the reshuffle boundary to be wrong.

### The shared-table clocks were never connected
`create-session` passed `{bettingSeconds, insuranceSeconds, actionSeconds}` to a
type declaring `{betMillis, actionMillis}`. Because `supabase/functions` is
excluded from `tsconfig.json`, nothing objected: `betMillis` read `undefined`,
`deadlineFrom` returned null, and every shared table ran with **no deadline at
all** — so `RESOLVE_TIMEOUT` could never fire and the documented "timeouts are
predictable and stated" guarantee was not in force anywhere it mattered.

`assertTimingIsCoherent` now rejects that shape at `createGame`, and the clocks
are measured rather than assumed:

```
private table   deadlineAt → 15 s
tournament      deadlineAt →  7 s   (the specification's figure)
solo table      deadlineAt → null   (a lone player stalls nobody)

RESOLVE_TIMEOUT 200 accepted
seats           a4b7:4980 locked  f012:4980 locked
```

Both absent seats were staked the table minimum and the hand went on, which is the
stated default rather than basic strategy played on someone's behalf.

### Betting closed on the first player to lock
Found while playing the first real four-player tournament. The cascade counted
"contenders" as seats with `originalBet > 0`, so a seat that had not bet yet was
not counted at all and the first player to lock closed betting for the table:

```
hand  1 settled       a676:10000 78fe:9900 0499:10000 6132:10000
hand  2 settled       78fe:9900  95ec:9800 990c:10000 a676:10000
```

One stack moving per hand, at a four-seat table. The tournament's structure was
correct — the elimination and the placements all worked — but it was not a
four-player game. Betting now closes when every seat that CAN play has locked,
and the betting deadline is what stops an absent player stalling the table:

```
hand  1 settled       a676:9200 78fe:9900 0499:9800 6132:9600
```

### An ordinary hand was eliminating the lowest stack
One function served both "who is bankrupt" and "who goes out at the hand-six
boundary", and calling it after every hand turned the format into "lowest stack
out every hand". A measured run eliminated three of four players by hand three and
settled the tournament nine hands early. `decideBankruptcies` and
`decideElimination` are now separate functions, so the ranked elimination cannot
be reached from an ordinary hand at all.

### A sudden-death hand consumed a scheduled hand
The specification calls tie-break hands "special" — extra hands at a boundary. The
first implementation counted them among the twelve, so a single tie at hand six
left the tournament playing eleven scheduled hands and raising its bet ceiling an
engine-hand early. `tournaments.scheduled_hands_played` now counts separately from
the engine's hand number: the ceiling follows scheduled hands, the button follows
hands dealt. Verified on a run with two tie-breaks:

```
bet ceiling per hand  2000 ×10 then 5000 ×4
scheduled_hands_played 12   tie_break_hands_used 2
```


### A ledger that could not be replayed
The money lens raced concurrent buy-ins on one account and produced this:

```
created_at                      delta   balance_after   reason
2026-08-15 23:21:15.613007+00   10000   10000           initial_grant
2026-08-15 23:21:15.633520+00   -2000    6000           table_buy_in
2026-08-15 23:21:15.633522+00   -2000    8000           table_buy_in
```

In timestamp order that reads 10000 → 6000 → 8000, which is not a valid chain.
Across the database, **34 rows** disagreed with their running total.

**No chips were affected.** Every wallet still equalled the sum of its own
deltas, no balance went negative, and no idempotency key repeated. Each
`balance_after` was correct for the order its row was *actually* applied in.

The defect was in the audit trail. `created_at default now()` records
transaction **start**, while `apply_wallet_delta` serialises on `select … for
update` — so a transaction that begins first can take the lock second and stamp
an earlier time on a later apply. `id` is a random uuid and orders nothing, and
the index reconciliation would use, `(user_id, created_at desc)`, sorted by the
wrong column. The table had no record of the order its rows were applied in.

An append-only ledger that cannot be put back in order is a weak audit trail:
any statement or dispute view built on it would render a history that never
happened.

Fixed by `20260815180000_wallet_ledger_apply_order.sql`, which adds a `seq`
identity assigned at INSERT — under the wallet lock, so it is lock-acquisition
order. Re-racing twelve accounts afterwards:

```
ordered_by_created_at -> broken rows | 6
ordered_by_seq        -> broken rows | 0
wallet <> sum(deltas)                | 0
```

### "Reachable" was too weak a test — and the flow hid it
Decision Drills was linked from exactly one place: the **foot of the How to Play
article**. My earlier reachability check passed it, because a route with one
inbound link is reachable. But the specification says the Learn tab *includes*
Decision Drills, and a headline feature you reach only by scrolling to the end
of a different screen is effectively unreachable.

Worse, the audit flow concealed it. The step was written as
`runFlow: when: visible: ".*Drills.*"` — so when the Learn tab stopped offering
Drills, Maestro reported `SKIPPED` and **the run still passed**. The flow quietly
stopped visiting a screen it exists to check.

Both fixed: Decision Drills is now a card on the Learn tab, and the flow asserts
it unconditionally. A screen this flow is responsible for no longer gets a
conditional.

### 576 lines of dead code
`src/features/home/career-summary.ts`, `mode-catalogue.ts` and `shell-ui.tsx`
were written by an agent whose Home screen was later replaced. Nothing imported
them. One of them asserted, in a comment, that `src/features/career` "does not

An orphan scan across `src/` and `shared/` now reports **zero** unreferenced

### The avatar was not targetable
`ScreenHeader`'s profile button carried an `accessibilityLabel` but no `testID`.
On iOS those are different things: the label is what a screen reader speaks, the
identifier is what an E2E flow selects. The same mistake had already been made

### No way out of a long screen
Every pushed screen — How to Play, Strategy Guide, Drills, Stats, Profile,
Settings, Fair Play — carried its only back control at the **foot** of the
content. How to Play scrolls for several screens before reaching it. iOS
edge-swipe worked, but a gesture is undiscoverable and unavailable to someone

Fixed with `src/components/ui/BackBar.tsx` at the top of all seven, labelled
"Back" rather than a bare chevron so it reads correctly aloud. `every-screen.yaml`

every screen it appears on.

### Assertions that verified nothing
Three E2E assertions passed while proving nothing, because Maestro matches text
**exactly** unless given a regex, and an `accessibilityLabel` replaces child text
in the tree. `"PRACTICE"` matched both Home's overline and the table header.
Rewritten around testIDs and explicit patterns.

## Known-unreliable and unverified

Recorded here so nothing above is read as stronger than it is.

- **The E2E flows are latency-sensitive on a dev build.** `practice-hand` and
  `career-node` failed once at 30s/15s waits and passed at 40s/30s on the same
  commit; the first render after a fresh Metro bundle is slow. Timeouts were
  raised rather than assertions weakened. A flow that fails twice at the raised
  timeout is a real defect, not latency.
- **The three racing tests in `tests/server` are load-sensitive.** They passed
  in isolation and across repeated full-suite runs, but failed once during a
  full run — twenty simultaneous requests against a single local Deno process
  while forty-three other test files run in parallel workers. The assertions are
  deliberately left strict rather than softened to absorb saturation. If this
  recurs, run `tests/server` on its own before concluding anything about the
  server.
- **`practice-resume.yaml` fails under Maestro** against a dev build. Resume
  itself is verified by direct observation; the flow races Metro's reload.
  Reconfirmed 2026-08-21 (phase 14 session 3): same assertion (`.*4,900.*`
  after relaunch), same timeout, every step before it — including the kill and
  relaunch — completed. Not re-attempted against a release build this session
  (EAS/production builds are session 5's scope). Excluded from the standard
  three-flow gate by omission: no script in this repository globs
  `tests/e2e/*.yaml`, and every documented "how to run E2E" list names the
  three flows explicitly and never this one.
- **The local database has been wiped at least once** by a container restart,
  which invalidated an earlier "pgTAP passing" claim until it was re-applied.
  Re-run `supabase db reset` before trusting any database result.
- **The Edge Functions are only verified locally**, never deployed.
- **Coverage gates are per-area**, not global, and now cover
  `supabase/functions/_shared` as well — when the strategy module moved there, its
  90% gate silently passed against zero files until the `include` was fixed. The
  server plumbing in that directory is deliberately ungated: it is verified by
  `tests/server/` against the running functions and scores zero under unit
  instrumentation, so a directory-wide bar would average real logic against it.
- **`tests/server` skips silently without Docker.** A skip is not a pass. The
  guard requires a 401 from the function, because the gateway answers 503 with
  the runtime stopped and an "any response" check reported the stack as up.
- **`supabase/functions` is excluded from `tsconfig.json`.** Nothing there is
  typechecked, which is how a timing object in the wrong unit disabled every
  shared-table deadline while `tsc --noEmit` stayed clean. Anything under that
  directory is verified by running it, never by compiling it.
- **The daily challenge's tie-breaks are still incomplete.** Decisions are now
  graded server-side and feed the weekly strategy board, but a daily ENTRY does
  not record its own accuracy or EV lost, so that board ranks on score then
  submission time. Marked ABSENT above rather than approximated.
- **The strategy module lives under `supabase/functions/_shared/strategy`.** That
  is not where domain logic belongs, and it is there because the Edge runtime
  cannot resolve anything else. `shared/strategy/index.ts` is a one-line barrel,
  so there is one implementation rather than two — but the layout is a
  concession to tooling and should be revisited if the CLI's resolution changes.
- **No push notification has ever actually been delivered.** There is no EAS
  project configured, so `getExpoPushTokenAsync` cannot issue a token, and the
  sender therefore always runs its mock transport. Everything either side of that
  gap is real and exercised — the permission flow, the token schema and its
  per-kind allowlist, the writes, the queue, the delivery record, the deep-link
  routing — but the last hop is untested against Apple or Google, and the
  database says `mocked` rather than `sent` so nobody can mistake one for the
  other.
- **Notification preferences are per DEVICE, not per account.** The allowlist
  lives on the push token row, which is the right scope for "this phone wants
  turn alerts" but means a new device starts from the Settings stored on it.
- **The Android channels are declared but never exercised.** They are created on
  Android only, and everything in this project has been verified on an iPhone
  simulator. A test asserts the ids the server stamps match the ids the client
  creates, which is the part that fails silently; the OS behaviour is unverified.
- **The E2E career flow takes about five and a half minutes.** That is the honest
  cost of playing ten hands through Maestro's per-check hierarchy dumps; earlier
  faster runs were faster because they were deadlocked and doing nothing.
- **Integration tests share one local database, so leftovers matter.** The
  sprint test drains the waiting tournament pool before registering, because a
  half-filled tournament from an earlier run splits its four players across two
  tournaments and neither is dealt. That was a real intermittent failure,
  reproduced on purpose before it was fixed.
- **A tournament needs four real accounts to start.** There is no bot filler and
  there must not be one — "never implement multiplayer as local fake players".
  A player alone in the queue waits, and the screen says how many seats are still
  open rather than pretending.
- **The sprint prize schedule is inflationary by design**: 2,000 of entry fees in,
  3,500 of prizes out, a net 1,500 chips created per completed tournament. Taken
  straight from the specification's figures and stated here rather than smoothed
  over.
