# Arc 21 — Phase 12, Production Release Candidate

**Date:** 2026-09-04
**Branch:** `phase14-s2-security`
**Code head this phase started from:** `08b0326` (documentation-only ahead of
`ac9ae0a`, which is the last commit CI verified)

This phase existed to try to DISPROVE that Arc 21 is ready to ship, to fix
whatever that turned up, and to leave the repository as the build I would submit

## B. What this phase found

Ordered by how much a player would have felt it.

### 1. Typed routes had been silently disabled, and three Quick Play controls led nowhere

`app.json` sets `experiments.typedRoutes`, which writes
`.expo/types/router.d.ts`; that file's module augmentation is the only thing that
makes `router.push("/nowhere")` a type error. `tsconfig.json` listed it under
`include` **and** listed `.expo` under `exclude` — and `exclude` filters
`include`, so the augmentation was never in the program. Typed routes checked
nothing for the life of the project.

What got through:

* `app/table/quick.tsx:194` — "Play Practice", `router.replace("/game")`
* `app/table/quick.tsx:199` — "Create an account", `router.push("/auth/sign-up")`
* `app/table/quick.tsx:345` — "Play Practice instead", `router.replace("/game")`

`/game` is not a route (the file is `app/game/practice.tsx`), and
`/auth/sign-up` is not one either (it is `/(auth)/create-account`). The third of
those is the specification's own recovery path for a player who cannot afford
the tier they picked — *"offer: lower tier / Practice / eligible Recovery
Grant"* — so an empty balance ended on expo-router's unmatched-route screen.

Fixed, and gated twice. `tsconfig.json` no longer excludes `.expo/types`
(putting the augmentation back), and because that file is GENERATED and
gitignored — so a fresh checkout would typecheck clean with no route checking at
all — the real gate is
`tests/contracts/every-route-target-exists.test.ts`, which reads the route tree
off disk and the navigation targets out of the source and needs nothing
generated. **Proved to fail on the breach**: reverting the three targets makes it
report all three, by file and line. `tests/e2e/dead-ends.yaml` then presses each
control on a device and asserts where it lands.

### 2. Any bad `arc21://` link was a dead end

There was no `app/+not-found.tsx`, so expo-router fell back to its own
`Unmatched` page: a light-themed developer screen reading "Unmatched Route / Page
could not be found", whose one control is `<Link href={pathname} replace>` — the
same unmatched path. On a cold start from a deep link there is nothing behind it
either, so a player who followed a stale invitation had no way back into the app.
`arc21://` is a public URL scheme; anything on the device can open one.

Fixed with a real screen that says what happened and offers Home and Practice.
Driven on device by `dead-ends.yaml`, which asserts the app's own copy is present
and expo-router's is not, then taps the way back.

### 3. A departed player was drawn at the table for ever, and the sentence was untrue

At a two-seat private table, after the host cashed out, the remaining player was
left looking at `0 · Yet to bet · Disconnected — their clock keeps running.` for
the rest of the session — photographed on a Release build during this phase's
two-simulator run.

Both halves of that are false of somebody who has LEFT, and this engine has no
other kind of disconnection; the reducer says so in as many words: *"`connected`
is only ever cleared by LEAVE, by a table closure or by a tournament elimination,
and nothing sets it back."* `isVacatedSeat` cannot help — it lets a NEWCOMER
reuse a slot at a public table, and nobody new ever joins a private room.

One of the three cases does leave a clock running, and it is the one the sentence
was written for: a player who leaves MID-HAND is `connected: false` immediately
while their committed hand goes on resolving. So the fix tells them apart.
`src/features/table/seat-presence.ts` is a pure predicate over fields
`PublicSeat` already carries, `tests/table/seat-presence.test.ts` covers all
three states constructed from what each code path actually leaves behind, and the
screen was re-photographed after the fix: **"No longer playing at this table."**
`sittingOut` is now rendered too — a seat below the table minimum, or a
tournament's sudden-death hold-out, used to be indistinguishable from one still
deciding.

### 4. The repository advertised an analytics integration that does not exist

`.env.example` declared `ANALYTICS_WRITE_KEY` under a comment saying "analytics
falls back to a console adapter", and `docs/RELEASE.md` listed "a vendor-neutral
interface with a console adapter" as something that already existed. **There is
no analytics module in this app at all** — no provider, no adapter, no
interface, and nothing reads that variable. `docs/PRIVACY.md` says, correctly,
that no analytics provider is configured; the other two contradicted it.

Both fixed. The variable is gone from `.env.example`, replaced by a note saying
why it is gone.

### 5. The build shipped a Face ID permission for an API it never calls

`expo-secure-store`'s config plugin writes `NSFaceIDUsageDescription` by default.
Arc 21 stores the session with `keychainAccessible:
WHEN_UNLOCKED_THIS_DEVICE_ONLY` and never passes `requireAuthentication`, so
Face ID is never invoked — and the string shipped was the plugin's boilerplate
("Allow Arc 21 to access your Face ID biometric data"). Same family as the
microphone permission phase 10 removed: **a plugin's defaults are permissions you
are shipping.**

Fixed with `["expo-secure-store", { "faceIDPermission": false }]`. Verified in
the built app: the Release `Info.plist` now contains **no usage-description key
at all**.

### 6. The privacy manifest declared no collected data while the app collects five kinds

`ios/Arc21/PrivacyInfo.xcprivacy` carried the required-reason API declarations
(file timestamp, user defaults, system boot time) and `NSPrivacyCollectedDataTypes`
as an **empty array**, which is Expo's template default. Arc 21 collects an email
address, a user id, gameplay records, profile content and a push token.

`app.json` now declares all five through `ios.privacyManifests`, each `Linked:
true`, `Tracking: false`, purpose `AppFunctionality`, taken from `docs/PRIVACY.md`
rather than invented. The identifiers were checked against Apple's own
`NSPrivacyCollectedDataType` and `NSPrivacyCollectedDataTypePurposes` lists.
Verified in the built app: the merge preserved the required-reason entries and
added the five.

The App Store Connect **App Privacy questionnaire** is the authoritative
declaration and is an owner action; the manifest and the questionnaire must
agree, and the manifest is now the thing they can be made to agree with.

### 7. Android shipped "Display over other apps"

The generated `AndroidManifest.xml` carried
`android.permission.SYSTEM_ALERT_WINDOW` in the MAIN manifest, from the React
Native template's dev overlay. Nothing in Arc 21 requests it and no release code
path uses it. `android.blockedPermissions` now strips it; verified in the
regenerated manifest (`tools:node="remove"`).

The two `maxSdkVersion="32"` external-storage permissions were left alone
deliberately: Expo writes them for `expo-file-system` on old devices, and this
machine cannot build or run Android at all, so removing a permission that cannot
be tested would be a guess.

### 8. `eas.json` named EAS Update channels for a project with no `expo-updates`

All three build profiles carried `"channel"`, which selects an EAS Update
channel. `expo-updates` is not a dependency and OTA updates are not in the MVP,
so the field named a mechanism the app does not have. Removed. `environment` is
kept on each profile: that selects EAS-hosted environment variables, which is
exactly how the two `EXPO_PUBLIC_*` values will be supplied.

### 9. iPad was declared supported with no iPad layout, under a rule that has changed

`ios.supportsTablet` was `true`. The generated `Info.plist` allowed all four
orientations on iPad (`UISupportedInterfaceOrientations~ipad`), and no tablet
layout has ever been designed, reviewed or tested. Apple's position changed with
iPadOS 26: **`UIRequiresFullScreen` is now ignored and iPad apps are expected to
support all orientations and dynamic resizing**, so an iPad-native declaration
can no longer be narrowed by a plist key.

Measured rather than assumed: the Release build was installed on a **13-inch
iPad Pro (M5)** and driven to a dealt Practice hand. It renders correctly in
portrait — a centred column with a lot of vertical whitespace — which is the
specification's "tablet layouts MAY expand gracefully". Landscape and arbitrary
window sizes have never been looked at, and this environment cannot rotate a
simulator programmatically.

The specification's design target is *"phone portrait"*, the acceptance criterion
is *"Portrait phone layout polished"*, and nothing in the MVP asks for iPad. So
the declaration was changed to match what exists: **`supportsTablet: false`**,
`TARGETED_DEVICE_FAMILY = 1`. The app still installs and runs on iPad in iPhone
compatibility mode — the one layout that has been designed and tested — and the
mandatory 13-inch iPad screenshot set is no longer required. A real iPad layout
is V1.1 scope, listed as such below.

### 10. The account-cleanup script could not play a table out of `INSURANCE_OFFER`

`scripts/e2e-account.ts` exists so an abandoned table cannot strand the account
that later runs need. It answered `INSURANCE_OFFER` with `DECLINE_INSURANCE` from
its own seat — which is correctly refused when that seat has already decided and
the phase is being held by somebody else's PENDING decision, which is the normal
state of a tournament table with three absent players. It threw, the account
stayed seated, and `public-matchmaking.yaml` was then told **"You are already
seated at a table"** — the product working exactly as designed, presenting as a
matchmaking regression.

This is the FOURTH helper in this repository caught by the phase after betting
closes (`reachPlayerTurns`, `dealAHand`, `standToSettlement`, and now this one).
Fixed: a refusal falls through to `RESOLVE_TIMEOUT`, and if the deadline has not
passed it waits and asks again, bounded. Verified against the very table that had
stranded the account — "played out a hand left mid-play, then cashed out".

### 11. A sign-in flow that walked around onboarding left every later flow photographing the carousel

`mc-sign-in.yaml` reached the auth screen by deep link, "because onboarding is
not shown to an app that has been used before". On a device that
`scripts/e2e-fresh-app.ts` has reset, onboarding IS shown — and the deep link
skips the button that writes `onboarding:completion`. So the flow signed in and
left the flag absent; `app/index.tsx` reads it on every launch, so every later
flow beginning `launchApp` + `assertVisible: header-chips` failed against the
onboarding screen. `two-client-public-leave.yaml` failed exactly that way.

Diagnosed by reading the device's own SQLite store, which held `auth:guest:v1`,
`practice:session` and `practice:stats` and no onboarding record, while the other
simulator — which had gone through the button — held all four.

**The app is right to re-show it.** The flag records that the 18+ and
no-monetary-value disclosure has been seen, and somebody who arrived by deep link
has not seen it; re-showing costs seconds and skipping it is not acceptable at
any price. So the FLOW was fixed to go through the door rather than around it,
and the flag is now written. No product change.

### 13. A `when`-guarded tap is two reads of the screen, in 54 more places

`two-client-play.yaml` failed on a Release build with `Element not found:
bet-deal`, the failure screenshot showing PLAYER_TURNS with `Bet 20` and 13
seconds to act: at a SHARED table the guest's betting window is whatever is left
of one clock the host has already used part of, and the deadline expired between
the `chip-100` tap and the `bet-deal` tap. That is the product working exactly as
its own countdown says it will.

Every tap in that loop is `optional: true` now, and so are the 53
deep-link-dialog handlers across all 26 flows — the iOS "Open in Arc 21?" sheet
can dismiss itself between the `when` and the tap, and a tap at a dialog that has
gone is not a defect. What proves each block is the assertion after it; the tap
never was the evidence.

### 14. No audit flow had ever walked Inventory with a server present

`every-screen.yaml` visits Inventory on an UNCONFIGURED build, where the only
assertion it can make is about the apology. `every-screen-online.yaml` did not
visit it at all — so the one screen whose whole content comes from `my_inventory()`
and `my_loadout()` had never been asserted against a server. A stop was added:
`inventory-count` is a real figure, at least one tab is present, the unconfigured
apology is absent, and nothing on the screen says "Buy".

## E. Security

Re-run against the running stack after the database reset.

* **RLS** — every table in `public` and `private` has row-level security
  enabled. Five tables have RLS and no policy at all (`private.game_commands`,
  `private.game_state_private`, `private.career_drill_seeds`,
  `rate_limit_events`, `rate_limit_policies`), which is deny-all and deliberate.
* **Grants** — `anon` reaches four catalogue tables (`career_nodes`,
  `cosmetics`, `rulesets`, `tournaments`) by SELECT and one helper function, and
  nothing else. `authenticated`'s write surface is column-level and narrow:
  six profile columns, one notification column, three loadout columns, and
  inserts on `blocks`, `friend_requests` and `push_tokens`.
* **`deny_client_write`** covers 28 tables, and
  `20_authorization_surface.test.sql` asks the CATALOGUE which tables lack it
  rather than naming them.
* **Least privilege** — `service_role` reaches **0 functions and 0 tables** in
  `public`. `public.assert_client_authorization_surface()` returns clean.
* **Realtime** — `realtime.messages` carries three policies: presence is
  writable only on `presence:players`, and `game:<id>` is readable only by a
  seated player, with the topic string built FROM the row.
* **Secrets** — the shipped bundle carries no service key and no seed secret
  (`0` matches). `npx expo config --type public` carries no key, no URL and no
  secret. The only long secrets anywhere in the tree or in history are the
  PUBLISHED Supabase local-development defaults (`iss: supabase-demo`) and an
  obvious `sb_secret_abcdef0123456789` placeholder, all under `tests/`. No
  private key, certificate or provisioning profile is tracked. `.env.local` is
  gitignored and untracked.
* **The adversarial suites** — `rls-idor`, `rls-writes`, `object-substitution`,
  `hostile-payloads`, `economy-authority`, `economy-guards`,
  `public-state-contract`, `rejection-contract`, `bounded-reads`, `realtime` —
  all pass inside the 302-test server run.

**No known exploitable high or critical issue.**
